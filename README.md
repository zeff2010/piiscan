# App 个人信息保护合规检测平台 · v1.0.1

> 用一台 **root 过的 Android 手机** + **Frida** 做动态采集，自动走完一次 App 的
> 首次启动、隐私政策阅读、同意与后续使用流程，把「它到底收集了什么、什么时候收集的、
> 有没有先说清楚」落成一份带截图和调用栈的 HTML 报告。
>
> 这是「自动初筛」这一半：**高召回、可批量**，输出用于挑出哪些 App 值得人工精检，
> 不替代人工判定，也不构成法律意见。

---

## 一、它能做什么

| 能力 | 说明 |
|---|---|
| 首次启动取证 | 冷启动 → 首启弹窗 → 政策正文取全文 → 点同意 → 记录**同意之前**发生过哪些收集行为 |
| 政策正文抓取 | 结构树取字 + 内联超链接定位 + WebView / 系统组件外跳兜底；共享清单等子文档一并抓 |
| 界面自动遍历 | DFS + tab 铺开 + 价值排序，按时间分四段；同构列表抽样、空转熔断、外跳识别 |
| 收集行为归因 | 每个敏感 API 调用都带调用栈，归因到**业务帧**（App 自身 / 三方 SDK / 框架） |
| 报告 | 详细版（含全部证据）+ 对外版（跳过未测项，不贴无证据的图） |
| AI 增强（可选） | 看截图认政策入口、政策全文深读、把事件流写成自然语言；**不配模型也能跑完整报告** |

覆盖 25 个测评项，其中全自动 7 项、半自动 13 项、辅助 3 项、不可自动 2 项。
每一项在报告里只有四种状态：**未发现问题 / 疑似 / 发现问题 / 跳过未测（附原因）**。
「跳过未测」是刻意保留的 —— 没测到就不写没发现，这一条比多报几个问题重要。

## 二、环境要求

| 项 | 要求 | 备注 |
|---|---|---|
| Python | 3.9+（实测 3.13） | 只用标准库 + 下面三个包 |
| adb | Platform-Tools，`adb devices` 能看到设备 | 见 `docs/DEVICE_SETUP.md` |
| 测试手机 | **必须 root**，且能跑 `frida-server` | 版本要与 pip 里的 `frida` 一致（本版锁 16.7.18） |
| AI 模型服务 | **可选** | 不配就走确定性策略；要「看截图」才需要多模态模型 |
| 操作系统 | Windows / Linux / macOS | 采集串行，一台手机同一时间只跑一个任务 |

> 手机是硬门槛：没有 root 设备跑不了动态采集。平台能启动、能看界面，
> 但提交任务时会明确拒绝并说明原因，不会给你一份空报告。

## 三、部署（5 步）

```bash
# 1. 取代码
git clone <your-repo-url> piiscan
cd piiscan

# 2. 建虚拟环境（推荐，不污染系统 Python）
python -m venv .venv
# Windows:  .venv\Scripts\activate
# Linux/macOS: source .venv/bin/activate

# 3. 装依赖
pip install -r requirements.txt

# 4. 生成本地配置（这个文件已被 .gitignore 排除，不会误提交）
cp config.example.yaml config.yaml      # Windows: copy config.example.yaml config.yaml

# 5. 启动
python run_platform.py
```

浏览器打开 <http://127.0.0.1:8760>。

常用参数：

```bash
python run_platform.py --port 9000 --host 0.0.0.0      # 换端口 / 允许局域网访问
python run_platform.py --workdir D:/piiscan_out        # 换工作目录（APK 副本、报告、数据库都在这）
python run_platform.py --no-device                     # 本机没接手机的服务器模式
```

**首次打开时应该是「干净」的**：没有登记过任何手机（即使 `adb` 里连着设备，
也只会显示成「未登记」，必须先点「添加手机」才能用）、AI 显示「未配置」、
任务列表为空、统计全是 0。这是预期状态 —— 下面两件事要你自己做。

## 四、第一次运行要做的两件事

### 1）登记一台 root 手机（必做）

左栏 **「手机管理」→「+ 添加手机」**，按向导走 10 步（约 10 秒）：
检测 adb → 检查 root → 选 ABI → 检查/推送 `frida-server` → 启动 → 验证注入。

- `frida-server` 的版本**必须**与 `pip install frida==16.7.18` 一致。
  不一致时向导会直接失败并说明差在哪，不会「勉强能用」。
- 本机没有 frida-server 二进制时，向导会尝试自动下载到 `tools/frida/`
  （要能上 GitHub/外网）。也可以手动放到 `tools/frida/frida-server-<版本>-android-<abi>`，
  或用环境变量 `FRIDA_SERVER` 指定。
- **登记 ≠ 现在在线**。平台里一条设备记录同时看三件事：接入时验过 root、
  此刻 `adb` 里是 `device`、此刻 root 还在。任何一条不满足，这台就不算「可用」。

> 为什么强制你先选手机、且不给你默认值：设备型号和序列号会写进报告，
> 是一份**证据**的一部分。替你默认选一台，等于替你伪造证据。

### 2）配置 AI 模型服务（可选，不配也能跑）

左栏 **「系统状态」→「AI 模型服务」→「+ 添加配置」**。可以存多套，随时启用/停用，
点「测试」当场验证连通性。

三种常见配法：

| 场景 | 填法 |
|---|---|
| 本机 Ollama | 类型 `Ollama`，地址 `http://127.0.0.1:11434`，文本模型 `qwen2.5:7b`，视觉模型 `qwen2.5vl:7b` |
| DeepSeek 云端 | 类型 `DeepSeek`，密钥 `sk-...`，文本/视觉都填 `deepseek-flash` |
| 内网 vLLM / LM Studio | 类型 `其他 OpenAI 兼容接口`，地址填服务端 `/v1` 前缀 |

三点必须知道：

- **「看截图」要的是多模态模型**。纯文本模型不会报错，而是静默回退到规则策略 ——
  所以配置列表会如实标出这一条能不能看图。
  DeepSeek 里 `deepseek-flash` 能看图，`deepseek-v4-pro` 只读文本。
- **没启用任何配置 = AI 关闭**（连请求都不发）。这和「配了但连不上」是两件事，
  报告里会分开写，因为「AI 到底有没有参与」本身就是要回答的问题。
- 密钥只存在本地 SQLite，界面只显示末四位；编辑时**留空表示不修改**。

细节见 `docs/AI_SETUP.md`。

## 五、跑一个任务

1. 「新建任务」→ 上传 APK 或填下载链接 → **选测试机**（必须自己选）
2. 选检测档位：

   | 档位 | 时长 | 范围 |
   |---|---|---|
   | `pre` 预检 | 150 秒 | 只取政策、不点同意、不登录 |
   | `light` 浅检 | 300 秒 | 只到二级页面，不登录 |
   | `deep` 深检 | 900 秒 | 可登录，覆盖主要功能 |
   | `extreme` 极限 | 3600 秒 | 长跑，截图 160 / 事件 40k |

3. 开始检测。任务**严格串行**（一台手机同时只跑一个 App），队列里可暂停/恢复/停止。
4. 完成后「查看报告」。

> 登录辅助：填了手机号时，遇到登录页会自动填号并点「获取验证码」，
> 然后等你在平台上回填验证码 —— 验证码不会自动读取。超时按「登录未完成」如实记录。

### 命令行单跑（不经界面）

```bash
python run_scan.py -p com.example.app -s <serial> -t 120 --deep -o out/report.html
python run_flow.py -p com.example.app            # 走完整 SOP 九阶段
```

## 九、常见问题

**Q：换了台电脑部署，Web 页面正常，插上手机却显示「未检测到测试机」**
先看提示里写的是哪一种，别猜：

- 写「**未找到 adb，无法检测设备**」→ 那台机器上平台没找到 adb，与手机无关。
  装 platform-tools，把它的目录加进 PATH，或设环境变量 `ADB` 指向 `adb`（`adb.exe`），
  **然后重启平台服务**（环境变量只对新进程生效）。
- 写「未检测到测试机」+「设备列表是空的」→ adb 可用但一台都没看到：USB 调试没开、
  手机上没点「允许 USB 调试」、数据线只能充电、Windows 缺厂商驱动、
  或别的 adb（手机助手/Android Studio）抢了 5037 端口（`adb kill-server` 后重试）。
- 出现 `unauthorized` → 在手机上点「允许 USB 调试」。

提示的第二行会写出平台实际用的是哪个 adb（完整路径 + 来源），
方便核对「我在命令行里明明能看到手机」这种情况 —— 多半是两者用的不是同一个 adb。
详见 [docs/DEVICE_SETUP.md](docs/DEVICE_SETUP.md) 第 1 节。

**Q：接入手机卡在「检查 frida」**
版本不匹配最常见。`pip show frida` 与设备上 `frida-server --version` 必须相同；
本版锁定 `16.7.18`。另一个原因是手机上的 `frida-server` 没启动或没执行权限。

**Q：`adb devices` 显示 `unauthorized`**
在手机上点「允许 USB 调试」。如果 auth 弹窗一直不出来，`adb kill-server` 后重插。

**Q：提交任务报「请先添加手机」**
这是设计如此：没在「手机管理」里登记过的设备不参与统计与任务，
即使 `adb devices` 里能看到。

**Q：AI 显示已启用，但报告里写「回退到确定性策略」**
两种情况：模型不支持图片（看配置列表上的标记），或调用失败被降级。
任务日志里会写清是哪一步、什么错。

**Q：点「停止」之后任务还显示「停止中」**
在途的模型调用会被立即打断；如果注入调用卡在设备上，最多等 1 分钟强制收工。

**Q：Windows 上中文乱码**
控制台用 `chcp 65001`。报告本身是 UTF-8，浏览器里正常。

## 十、边界与免责

**它不做什么**

- 不做脱壳、不做反调试绕过。遇到加固 App 时注入可能被拦，此时会退回
  「系统侧旁路取证」：`dumpsys appops` / `dumpsys package` 能看到「用过哪些权限」，
  但**没有调用栈、无法归因**，报告里写「待人工确认」，**不作为认定依据**。
- 不做网络抓包。没有抓到报文就不会说「数据外发」，这一条是硬约束。
- 不替你下结论。自动判定只用于筛选，最终认定要人工复核。

**已知局限（如实写在这里，而不是等你自己踩）**

- 单台手机串行，没有并行采集。
- 登录态之外的功能（订单、个人中心深处）覆盖不到，报告会标「跳过未测」。
- 部分 App 的政策入口在系统组件里（跳到浏览器/内置 WebView），能取到正文，
  但不一定能拿到 URL。
- 加固壳、X5 内核 WebView 的取文与注入仍是弱项。

**合规提示**：本工具用于**自有 App 或已获授权**的合规自查。用它分析第三方 App 时，
请自行确认符合当地法律与授权范围。报告产出的是技术观测记录，不是法律意见。

## 十一、内置数据说明

`reference/` 下的清单由本项目整理与维护。条目都是**公开事实信息** ——
包名前缀、API 签名、权限名、域名、厂商名称；本项目做的是汇总、归一、去重与结构化，
不包含任何他人的分析结论或文字作品。

- **权限名与保护级别**：Android 框架公开定义（AOSP，Apache-2.0）
- **敏感 API 签名**：Android 框架公开接口（AOSP，Apache-2.0）
- **SDK 包名、域名、加固特征**：各 SDK 与厂商公开文档中的包名前缀、域名、so 文件名，
  以及与之对应的企业名称。相关名称与商标归各自权利人，本项目仅用于识别与报告归因，
  不表示任何关联、认可或赞助

v1.0.1 的规模：

| 文件 | 条目 | 内容 |
| --- | --- | --- |
| `sdk_package/sdk.json` | 2905 | SDK 包名前缀 → 名称 / 类型 / 厂商 |
| `sdk_package/sdk_alias.json` | 2 | 同一 SDK 的其它包名根（附真机取证记录） |
| `sdk_package/jiagu.txt` | 74 | 加固特征 → 加固名称 / 厂商 |
| `static_word/sensitive-api-static-api.json` | 61 | 敏感 API 签名 → 类别 / 行为码 / 所需权限 |
| `static_word/privacyconfig.txt` | 24 | 行为码 → 隐私政策常见表述词 |
| `static_word/permission.json` 与 `.txt` | 524 | 权限 → 中文名 / 说明 / 保护级别 |
| `static_word/WebSiteHost.txt` | 194 | 域名 → 企业名称 |

整理这批数据时做过的处理，都写在各文件开头的说明里：

- **分类归一**：SDK 类型原有三十种写法（`广告和变现` / `广告/推广` / `营销和互动`…），
  合并为十七种，报告里的「类型分布」才有可比性
- **去重**：包名、域名、加固特征按规整后的键去重
- **修正错项**：同一个行为码被两条不同语义的条目占用、行为码写成中文、空行为码，
  都按语义改正
- **补全**：政策词表里有、API 表里缺的八类（通讯录 / 短信 / 通话记录 / 日历 /
  粗略定位 / Android ID / OAID / 内容提供者）补齐对应签名

这些文件是可扩充的数据，不是代码的黑盒：格式写在文件头部，增删条目不需要改代码。
识别库没收录的 SDK，报告里写「未识别」——这不影响「是否违规」的判定
（判定依据是运行期的 API 行为，不是 SDK 名单），只影响责任主体归因的细致程度。
